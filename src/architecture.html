Architecture de Gitdrop

Un cœur Node/TypeScript partagé, deux façons de l’utiliser (CLI et interface locale), et le vrai git pour publier.

Vue d’ensemble

La CLI et le serveur local appellent exactement le même cœur : un comportement identique, testé une seule fois. L’interface est une application React compilée en fichiers statiques, servie par le serveur local.

Le pipeline d’un push

Préparation des fichiers
.gitignore, README, licence, .env.example et CI générés si absents ; dépôt Git initialisé ; dossiers techniques et fichiers exclus écrits dans .git/info/exclude, sans toucher aux fichiers du projet.
Commit local
Si la machine n’a pas d’identité Git, l’auteur est le compte GitHub (adresse noreply).
Création du dépôt GitHub
Seulement maintenant : une erreur locale ne laisse jamais de dépôt vide. Un dépôt vide homonyme (push interrompu) est réutilisé.
Push sur main
Avec le vrai git. En mode « historique propre », un seul commit est créé à partir de l’arbre courant ; l’historique local reste intact.
Pages (optionnel, non bloquant)
Pages est activé avant d’ajouter le workflow dans un second commit, pour que son premier run n’échoue pas. Un échec ici n’annule pas le dépôt.

Système de sécurité

Jeton GitHub

Stocké dans ~/.config/gitdrop/config.json en 0600 (écriture atomique). Transmis à git par variables d’environnement : absent de l’URL du remote, de .git/config et de la liste des processus.

Serveur local

Écoute sur 127.0.0.1 uniquement, exige une clé aléatoire générée à chaque lancement, et vérifie Host et Origin : les autres sites web et le DNS rebinding sont bloqués.

Secrets

Règles par fournisseur avec lien de révocation, détection par entropie, scan de l’historique (toutes branches, 64 Mo max, 30 résultats). Les secrets sont exclus même si le .gitignore est désactivé.

Archives .zip

Protection zip-slip, taille déclarée vérifiée avant extraction (zip bomb), 90 Mo envoyés, 200 Mo extraits, 50 000 fichiers max. Espaces de travail purgés après 3 h.

Capacités et limites

Ce que Gitdrop fait

  • Publier un dossier ou un .zip sur un compte GitHub personnel
  • Détecter la stack (Next.js, React, Laravel, Python, Flutter, Go…)
  • Protéger les secrets : fichiers, contenu, historique
  • Générer .gitignore, README, licence, CI, .env.example, topics
  • Publier sur GitHub Pages (statique, Vite, CRA)
  • Branche + pull request, watch, undo

Ce qu’il ne fait pas (encore)

  • Organisations GitHub, GitLab, Bitbucket
  • Pages pour Next.js, Nuxt, SvelteKit (rendu serveur)
  • Git LFS : les fichiers de plus de 90 Mo sont ignorés (limite GitHub : 100 Mo)
  • Réécrire l’historique d’un dépôt déjà publié
  • Fonctionner sans Git installé

Qualité

46 tests : 11 unitaires (règles de secrets, entropie, workflows Pages, messages de commit) et 35 de bout en bout. Ces derniers lancent le vrai CLI contre un faux serveur GitHub (REST, Device Flow, Pages, pull requests) et de vrais dépôts Git « bare ». La suite est rejouée contre le paquet npm installé proprement et contre le binaire autonome.

Les tests simulent GitHub : un premier vrai push reste la meilleure validation avant de publier.
